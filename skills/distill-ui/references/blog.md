# 一个不含设计的skill

> 一个元 skill 的来龙去脉:distill-ui 自己不含任何设计,却能沿五层对话,把一个组织的设计系统铸成可加载的 ui-skill。本文以对话中 AI 的第一视角记述。它是 [distill-ui](../../../README.md) 这个 SKILL 的理论源头,也是 [distill](../../distill/SKILL.md) 的对话模式第二次上岗的故事。

## 起点:五层骨架

他这次来,不是带着困境,是带着一张地图。

> 我计划做一个新的skill. 作用是协助构建一个设计系统。几个要素是 设计原则,核心基础层,组件与模式层,文档与知识层,治理与运营层。设计原则是用来指导核心,组件。文档是用来做快速查询,治理是规模扩大后,确保不同使用方保持一致的方式。

我的第一反应,是把它当成一份章节目录:他想做一个教 AI 建设计系统的领域 skill,五层就是五章,原则管指导,文档管查询,治理管一致。层次关系清晰,我顺着往下读,还认出一个熟悉的影子——治理放在第五层而不是第一层,像极了 micro-fullstack 里"基准形态加升级接缝"的克制:小项目不必一上来就全套治理。

于是我按领域 skill 的路数去问使用场景,从他自己的项目问起。

而真正的定位,藏在他的第一个回答里。

## 转折一:容器不装内容

> 这个 skill 是类似 distill 的一个 skill,他也是一个用来生产skill的元skill,未来其他人有设计系统需求的时候,都可以通过类似的对话形式,来快速确认自己的目标。以及基础的内容。

不是教 AI 建设计系统的 skill,是帮人把设计系统需求蒸馏成 skill 的 skill——distill 的姊妹篇。distill 把一段对话蒸馏成方法,distill-ui 把一个组织的设计系统需求蒸馏成设计系统。

定位一换,五层的身份跟着变了:它们不再是 skill 的内容,而是对话的地图。distill-ui 自己不含任何配色、任何组件、任何原则——那些东西要在对话里,从需求方身上一条一条问出来。

管线在接下来的几轮里成形:

> 比如用户加载 distill-ui 后,会对话告诉他,五层要素是什么,然后会产出 ui-skill

> 其他用户加载这个 ui-skill 后,就会自动获取到token定义,组件定义之类的

这是一条两级火箭。第一级 distill-ui 只点火一次,把需求方脑中的隐含判断铸成 ui-skill;第二级 ui-skill 长期在岗——此后任何 AI 会话要写界面,加载它,token 与组件规范即取即用。一致性的边界,就是 ui-skill 的分发范围:发给谁,谁的 AI 产出就与源头一致。

我问五层的出处,他答得坦白:

> 当前五层是设计系统领域的通用说法。也是核心的内容。

地图是现成的,从领域里借来。但地图不等于旅程:沿这张地图能问出什么,取决于坐在对面的那个人。新意不在五层,在管线。

## 转折二:治理不在项目里,在产品之间

轮到我收敛了。我提议让对话学会掂量规模:小项目把治理砍到只剩最小件,规模大了再展开——基准形态加升级接缝,和他自己的 micro-fullstack 一个思路。

他把这个提议推了回来:

> 治理层不是为了单个项目而设立的。比如 a b c 分别使用了 1.0 1.1 1.2 不同的版本,但是又是同一家公司的多个产品,此时必然会出现视觉交互不一致的情况。甚至可能最基础的设计原则也有可能发生变动。而治理是为了让不同的产品也能够保持一致。

我错把治理装进了单个项目的边框,当成"项目长大后的内部事务"。他把它搬到了项目之外:治理的对象根本不是项目,是资产——一份被多个产品共享、被版本切开、随时间演化的资产。

这份资产有两个漂移轴。空间轴上,A、B、C 三个产品锁在 1.0、1.1、1.2 三个版本,视觉与交互的漂移不是事故,是必然;时间轴上,连最基础的设计原则本身都会变,原则变了谁拍板、怎么通知、旧版本怎么跟上,才是治理的真题。

于是对话里的问法也换了:不问项目多大,问这套设计系统服务几个使用方。一个使用方,治理收缩成一句话;产品成群,治理才展开成版本、变更、升级、审计的全套。深度不随规模,随消费方。

## 最后两针

理论看起来已经齐了,他又补了两针,都落在产出的成色上。

第一针,文档层的读者从来不是一种。

> 文档知识,同时也是要人类可阅读的。

AI 秒查是一半,人能通读是另一半。团队里的设计师、半年后入职的新人,要能拿这份文档当规范入门。速查表可以写给机器,正文必须写给人。

第二针,把治理从名词变成了动词。

> ui-skill 的升级要写在治理层中,在 ui-skill 自升级时,就能够告知,或者主动帮助用户执行治理动作。

ui-skill 要带着自己的版本号和升级手册上岗。产品侧的 AI 加载它,发现版本落后,就主动告知变了什么、要做什么,甚至直接代为执行——换掉废弃的 token,更新组件用法。治理不再是文档里躺着的一段话,而是加载那一刻发生的一个行为。设计系统到这里才算成了活物:它不只被遵守,还会自己走上门去要求被遵守。

## 终局:铸造者不含设计

对话结束时,成形的是一条管线和一张地图。

```
distill-ui(对话沿五层)→ ui-skill(原则 + token + 组件 + 文档 + 治理)→ AI 写界面即受约束
```

distill 从人机对话里蒸馏方法,distill-ui 从组织的需求里蒸馏设计系统——两个 skill 共享同一个信念:内容要从人身上问出来,skill 只是铸模。

而铸模要通用,自己就必须是空的。distill-ui 不推荐配色,不裁决风格,五层是地图,不是风景。

**铸造者自己不含设计,才铸得出每个人的设计。**

顺带一提,这次对话照例由 distill 收尾成文;而 distill-ui 铸出的 ui-skill 不再配 blog——铸模的来龙去脉留在铸模这里,铸出的 skill 只装操作指引。元 skill 家族的分工,连产出都分好了。

## 补记:theme 与原则,谁越了权

distill-ui 落笔之后,他又回来撞了一下,这次撞在 theme 上。

> 一些组件库或者设计系统。他们会带有 theme 相关的概念。你认为设计系统需要带这种东西吗?theme 是否很容易和设计原则产生冲突?比如原则规定使用红色来表示危险动作的二次确认。但是在 theme 中危险色可能会被定义为其他颜色。

这看上去像一场权斗:原则说红,theme 给了橙,谁赢?拆开才发现根本不是对抗,而是层级错位。"危险动作用红色"这条原则,写在了字面层——它在深色模式下天生违法:深色里的危险色本来就该换一个红,可访问性的对比度也逼着它变。一条原则若不许系统合法地变化,它就没有站在正确的层级上。

修法是让三层各归各位。原则说语义:"危险的二次确认必须用危险语义色";原则也可以保留一小块对字面的管辖——划值域:"危险色永远在红色系取值",这是 theme 自由的边界;而 theme,是对语义槽的一组命名赋值,在值域内浅色选一个红、深色选另一个红。token 由此必须是两级的:字面档供料,语义槽供用。

诊断也随之分开了:原则里出现具体值、被主题的合法变更顶翻,病在原则,升格为语义或降为值域;主题把 danger 槽赋成品牌绿,病在主题——那已经是重设计,不是换肤。宪法、法律、行政令:行政令永远不能修宪。

三颗螺丝随即进了 skill:设计原则对字面值免疫;token 两级,theme 定义为槽位赋值集;theme 换值是低版本动作,换语义是主版本。反过来看,theme 的存在恰好是语义层稳定的证明——换一套主题,组件一行不改。而"要不要深浅色、服务几个使用方",对话第一步本来就会问:老旋钮,又拧住了一个新东西。

## 补记二:离场的铸造者,与回家的词汇

落笔之后,他没有走。review 找出的缺口摆在桌上,这一轮磨的是 distill-ui 自己,上场收尾的照例是 distill。

第一站是两级 token。spec 写了"字面档供料,语义槽供用",却没规定"用"——我提议绝对禁令:业务代码里不许出现字面值。他把工程现实摆了进来:

> 工程实践中,有语义的,需要优先走语义,但是可能存在工程师不知道语义,ai 没有扫描出来语义的情况。所以实际使用阶段是允许走字面量。但是要有待改进记录。

于是账本出现了:记在使用方仓库,与版本记录同处。记什么、谁清账,他两句定音:

> 谁记录,谁清账。也就是谁使用了字面的token,谁对此处负责,应主动安排清账。

> 反复出现的字面,在累计过多后。清账人,应当使用 skill 进行提炼,然后更新设计系统

账本由此不只是债——反复出现的字面量,就是缺失的语义槽。它成了系统的感官:使用侧的欠账攒够了,反过来喂给设计系统。

但我把这句里的"skill"读成了 distill-ui,顺手设计了"增长模式":清账人带着账本回来,铸造者二次开工。他把这推翻了:

> 当 ui-skill 创建出来后,未来的迭代和处理,只需要选择 ui-skill ,而不再需要 distill-ui。ui-skill 会附带自更新的能力

管线被拉直了,而且比原来更硬:第一级火箭只点火一次——这条写在本篇前半段的规则,这次从他手里学了回去。自更新从此是双向的:一手升使用方,核版本、宣读变更、代执行升级动作;一手长自己,从账本提炼新槽、拍板、升次版本、生成升级动作。扩展路径也一并自含:单使用方的治理文档里埋着休眠的骨架,第二个使用方出现时就地展开,谁也不必回到铸造者。

机制磨完,轮到手艺。三课,都记回了 distill。

第一课,提问。"该多硬?""写在哪?"——这种没头没尾的问法,他一句判了:

> 提问没有主宾,文字提问要明确待决策问题。

第二课,用词。"可访问性盘点"摆上桌,他不认识这个词:

> 可访问性盘点是什么?这个是新造词,从我说过的语言中,选择词汇描述。

他在 code-tree 里立过"词汇沿使用侧迁移"的规矩,这回轮到我自己的词被迁移。"深度旋钮""拧定""第〇步",一个个送回家。最后一个,他连选项都懒得挑:

> 就第一步。不要搞什么 0 步。

第三课,形式:

> 用ask 工具来提问。给我选项。

开放题换成选择题,能裁决的就不闲聊。

手艺之外,他还砍了两刀:交付前的实测,不要;五层地图里的无障碍问句,不加。我两次想往铸模里塞工序,他两次拆下来。合格线写在层里,是铸造时的成色标准,不是交付关卡;地图不预埋领域的问句,内容从需求方身上长——这条底线,连"正确"的工序也不得例外。

这一轮唯一新开的铸件是模板:

> 我们这次的 skill 是要带有相关模板的。这样用户才能够用 distill-ui 创建属于他自己的 ui skill

五段占位骨架,列名加尖括号,铸模第一次带上了内腔。内腔里依旧没有铁水:模板保证形状可复现,不替需求方省掉任何一次裁决。

收尾清点:这次 distill 上岗磨 distill-ui,磨出来的手艺又写回 distill 自己的正文。元 skill 家族第一次自己磨了自己——铸造者被磨,纪录写进磨刀石。
