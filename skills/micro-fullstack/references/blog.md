# 一套小微全栈栈是怎么被问出来的

## 一行栈清单，一句"你向我提问"

用户带着一个需求来：给技能库增加一个新 skill，内容是他为小微项目沉淀的技术栈。开场只有一条栈清单——vite、mpa、ssg、hono、pglite/postgresql、zenstack——外加一句授权：

> 其他的你向我提问。

我最初以为这是一次记录：把已知的结论誊写成规范即可。但清单是结论，不是方法。结论背后必须有判断，判断只能靠问出来。于是我开了三轮提问，每一轮都在推翻我上一轮的想象。

## "sharedworker 纠正一下"

第一轮我问他单机版提到的"shader worker"指什么，准备听他讲 GPU 渲染优化。回答只有四个字：

> sharedworker 纠正一下。

我把一个字母之差的两个概念彻底搞反了。SharedWorker 不是渲染技巧，是单机版的后端宿主——数据库和 API 层整个搬进这个浏览器自带的共享线程里。第二轮他把架构钉死：

> sharedworker 跑 hono + pglite, electron 只做薄层封装，不依赖 electron api 和进程模型。

这句里最锋利的是后半句。我原以为这会是一次"如何把 electron 集成进项目"的经验分享，实际上 electron 在这套方法里被降格成了一只壳：开窗、加载产物，仅此而已。业务代码里 grep 不到一行 electron import——壳坏了可以整只撕掉，不伤内部。

## "放 server"：部署单元变成了 API 的家

下一道悬案是 hono。单机跑在 SharedWorker，联机跑在 node，那 hono app 的代码放在哪个包，才能两边复用？他的回答：

> 放 server, 但是调整好导出，和 vite tsconfig 相关配置。

我又一次预期落空。我以为 apps/server 是"联机版的部署单元"，在他那里它是 **API 的家**——家只有一个，宿主有两个。hono 导出成一个 factory，数据源作参数：联机时 node 注入 postgres，单机时 SharedWorker 注入 pglite。同一套路由，两种宿主，靠 workspace 依赖和 tsconfig/vite 配置把缝接起来。

数据层同构。zenstack 的定义和插件单独成包，一份 schema 对两种数据库无感。关于分工他说得很清楚：

> zenstack 提供了丰富的 api, hono 要暴露出来

模型 CRUD 走 zenstack 挂到 hono，复杂查询自行查库。整套取向他用一句话收拢：

> 以单机为基础，向后兼容。

## SSG 是补丁，不是信仰

轮到前端，我给了四种 SSG 方案让他选，预设了"必须选一个"。他的回答拆掉了我题目的前提：

> ssg 主要用途是规避各种样式闪烁问题，解决没有路由的尴尬表现。

在这套方法里 SSG 没有默认地位。它是补丁：出现闪烁、出现"没有路由"的尴尬表现，才打上；症状不存在，就不引入这条构建链路。MPA 本身才是主干——每页一个目录、`main.tsx` 入口、vite 自动 glob 发现，glob 失效才退回手动维护 rollup input。

## 公理

收尾时我问他这套栈是怎么长出来的。他选了三个背景——重框架太重、SPA 体验问题、单机到联机的同构升级需求——然后补了一句：

> 用户需要一个快速能用的工具，不在乎具体形式。

这句话是整套方法的公理，前面所有的反预期都从这里推出。因为交付物是"快速能用的工具"，所以单机版是基准形态而不是降级形态；所以每层按最薄选型，演进能力交给接缝而不是框架；所以 SSG 是按需的补丁、electron 是可撕的壳、SharedWorker 这样反常规的宿主反而是最短路径——它让"联机版的架构"在零部署的形态里原样存在。

## 尾声：缝上的坑

方案定稿前，他补了最后一条纠正：

> 注意下，pglite 后端sharedworker 可能 opfs 会有问题，可以备选 idb

这条恰好落在整套方法最不寻常的地方：OPFS 的同步访问句柄只在 dedicated worker 里可用，而这套栈把后端安在了 SharedWorker 里。选型最反常规处，坑就在那里——备选方案必须先于故障就位。

故事讲完了，方法只剩三行：单机为基准，三种宿主共用一个 hono factory；一份 zenstack schema 对两种数据库无感；electron 永远站在树的最外层。三个接缝各自可撕，工具于是能从桌面上的一只壳，长成联机的服务，而代码还是那一套。
